## Execution controls and unresolved contracts

- Use Node **24+** (ADR requirement), a dedicated QA server port, separate Playwright browser contexts/cookie jars, and explicitly configured disposable SQLite files **inside the QA worktree**. Never touch a developer's/shared database; reset only QA-owned fixtures. Use deterministic seed IDs and capture fixture/version state for concurrency tests.
- The integrated server requires Node `>=24.0.0 <25`; the web package declares build, lint, unit, quality, delivery-integration, and Playwright scripts. Executed commands and results are listed in [`reports/current/EXECUTION.md`](../../../reports/current/EXECUTION.md); a fixture-only suite is not a substitute for live-server evidence.
- Obtain an approved per-route/per-role permission table (including both QA roles), legal transition edges and prerequisites, dependency semantics, review/test-run/defect/retest payloads and states, version requirements for those mutations, and the readiness truth table. The current documents do not fully specify these. Mark affected cases blocked during execution until clarified; never infer that every role may mutate or that a passed retest automatically closes a defect.
- Assignment/sprint organization and QA case management are MVP outcomes without complete route/schema definitions here. Confirm the contract with owners before automating these checks; do not expand the API or schema from QA.
- API tests must use real HTTP and SQLite, including denied requests and atomic rollback; mocked unit results cannot substitute. Playwright must target the built-client demo and API, not a static prototype. Real-time updates, external identity, hosted deployment, and production-security certification are outside scope.

## Evidence and readiness gate

For each execution, record actual PASS/FAIL/BLOCKED/PARTIAL evidence: tested commit SHA, Node/browser versions, exact command and exit code, fixture/database identifier, case IDs, and sanitized report/trace references. Do not record raw session cookies or real user data. QA-02 owns unit/API/automation evidence; coordinate UI/manual accessibility and defect retest evidence with QA-01.

The tested project reached the app's server-reported ready state and had no open blocking defect. This is not a production release recommendation: A04, A12, A13 and the specification gaps in the acceptance matrix remain partial or blocked; the approved authorization matrix and CON-12 review by TL-01/PM-01 are still required.
